# Course registration and delivery mode

The home action is 可登录课程. It opens a native Monday–Friday week grid, following the timetable's period layout. A cell with one candidate has a checkbox; a cell with multiple candidates displays a count and opens a native selection dialog. Dialog selection remains in activity state and is reconciled by stable course identity across successful reads. Only checked courses are submitted by the small footer action; there is no implicit select-all. Unscheduled/weekend candidates remain accessible through a compact count button. Nothing in this preview changes earned credits, GPA or the official timetable. The underlying school document is invisible and excluded from accessibility while remaining fully laid out for reliable parsing.

Full foreground sync now reads registration status after school notices. Only a live school table with a known academic year/term, unique course codes, available unchecked checkboxes and an unambiguous registration action can enable registration. The supplied guidance screenshot is contextual information for its faculty, not a universal opening schedule or personal CAP authorization.

Newly available courses produce an in-app dialog with course names, plus an optional system notification (existing notification settings and system permission apply). Identical snapshots do not repeatedly alert. Snapshots and alerts are keyed by student.

The native batch action lists the selected courses and requires a second confirmation. Immediately before clicking the school action, the adapter rechecks the live student, term, full course snapshot, selections and form ownership. It rejects stale snapshots, other preselected boxes, duplicate IDs and changed availability. A persistent pending flag and approved course IDs prevent accidental retries across activity or process restarts. A recognized school confirmation page is submitted only when its entire list exactly matches the approved IDs and its form remains on the school origin. A submitted request is **not** labelled successful: every approved course must be explicitly marked registered in the verified live account and term. Unknown results stop automation and remain pending for user verification. The app never submits during sync.

The parser is intentionally limited to recognized school table layouts; unknown layouts show a native status and do not enable submission. A recognized read-only timetable is accepted as a履修 status result, with no inferred eligibility, so it does not spin until a false network timeout. Dashboard navigation does not require a student number; reading and submitting still verify the number on the destination page. Unit and simulated DOM tests do not establish that a future live registration-period layout is supported. Real enrollment cannot be tested without the student choosing courses and confirming submission.

Delivery mode is now extracted from the value cell of オンライン授業／対面授業 in the school syllabus. Timetable sync only captures observed syllabus links, without issuing requests or waiting on syllabi. After all timetable and notice/registration queries finish, a separate final phase follows those links with two bounded read-only requests at a time. Its timeout never marks an already saved timetable failed. Values are saved by student, academic year and exact course code, and feed calendar blocks and exports. Real-time online, on-demand online, face-to-face and blended courses remain distinct. Previously reviewed cohort/session-specific exceptions retain their constraints. Missing data does not imply online delivery; existing saved data survives fetch failure.

Verification: `node scripts/test-school-registration.cjs`, `node scripts/test-school-syllabus.cjs`, Gradle `testDebugUnitTest` and `lintRelease`. The screenshot's course title is not used to guess a course code.

## Calendar navigation correction

Date-picker, month navigation, month day selection and previous/next week now use one date transition. It updates the date, displayed month and term together; the week number is derived from that date rather than stored independently. Manual year/term selection moves the date to that term's first displayed week. Previous/next week remains enabled across term boundaries.

Both week and month views use the current student's resolved events from all saved terms, deduplicated by date, period and course code with newest snapshots taking precedence. This keeps adjacent-term courses visible in a boundary week/month. Classroom and delivery labels retain each event's original year/term key. Navigation into an unsupported year never creates course events. Exports remain explicitly scoped to the selected term.

`SchoolCalendarNavigationTest` covers Q2-to-Q3 date selection, bidirectional week movement, Q4 across January, term-anchor round trips, mixed Q3/Q4 boundary weeks, monthly event inclusion and duplicate suppression.
